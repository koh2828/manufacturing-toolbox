# Future OCR Integration Plan

現行版にクラウドAI呼び出し、APIキー、課金処理、クラウドDBはありません。次の改善は、実際の誤読と確認時間を測定して決めます。API導入を既定の解決策にしません。

## 無料のローカル技術で改善する候補

最初に、ページの傾き推定、必要領域だけの高解像度再読取、処理中のプレビュー、テキスト層と画像の不一致検知、バックアップの分割、メモリ上限に応じた自動描画縮小を検討します。複数のOCR候補が一致したことだけで確認済みにせず、相違したセルを原本と並べることで確認を短くします。

同じ合成帳票だけに最適化しないよう、開発用とは別の検証コーパスを追加します。評価は文字列正答だけでなく、項目と測定値の正しい対応、Lot・境界、未検出誤り、修正操作数、確認時間、低メモリPCの挙動を含めます。

## テンプレートで改善する候補

サプライヤーごとの見出し・終端・表の段組み・継続ページ・改訂版の識別を改善します。ユーザーが確認した項目名／製品名の別名、よく使う試験方法、期待する項目一覧を再利用すれば、欠落候補を見つけやすくなります。規格内の値になるよう自動補正することは避けます。

別名やルールの保存はOCRモデルの学習ではありません。変更したルール、適用した版、候補値、元のOCR文字列を追跡できるようにします。テンプレートは端末内で保存し、明示的にJSONで移行する方式を維持します。

## 高度なローカルモデルを検討する条件

PDF.js＋Tesseractで残る複雑な表、縦書き、低品質スキャンに対し、PaddleOCR.jsなどの検出・認識モデルを同じ正解データで比較できます。ONNX Runtime Webはその実行基盤候補です。まだこのリリースでは精度・速度を実測していないため、Tesseractより優れるとは主張しません。

採用基準は、誤った項目―値対応と必要な人手訂正が減ること、日英両方で悪化しないこと、初回ダウンロード・メモリ・CPU/GPU条件・Worker対応・ライセンスが許容できることです。WebGPU非対応の社内PCでも利用できる経路を残すか、非対応を明示します。大きなモデルを無条件に既定配信しません。

## 将来クラウドOCRを比較する価値がある条件

未知のレイアウトや複雑な多段表が大量にあり、テンプレート作成・ローカル再処理を含む確認工数が依然として高い場合には、クラウドOCRの候補を比較する価値があります。ただし、帳票の送信許可、契約、保存期間、学習利用、処理地域、ログ、委託先、費用を別途判断する必要があります。性能や正確性は、同じ盲検コーパスと人の確認時間で評価します。

実装する場合も、ローカル処理失敗を理由に自動送信しません。対象ページ・送信先・送信内容・費用をユーザーが理解して明示的に実行する独立した操作にします。企業の許可がないデータを使ってPoCを行いません。APIキーを公開フロントエンドへ埋め込まず、資格情報の扱いと必要なサーバー構成はその時点で別途設計します。

## 交換可能な契約と維持する境界

現行の `DocumentEngine.create()` と `processFile` / `render` / `cancel` / `dispose` を交換点にします。どのエンジンでも、原文、ページ、原本位置、抽出用位置、方式、エンジン・モデル版、処理設定、参考信頼度、エラー、処理時間を同じ形式で返します。下流のテンプレート、検証、確認、検索、Excel、品質解析を再実装しない構成です。

クラウド由来を含むすべての新規出力を未確認で受け取り、人の訂正とモデル候補を区別します。未確認値、検出限界値、範囲値を確認済みの一点測定値として渡す経路を作りません。推定した単位・日付・製品の同一性を確定値にせず、曖昧さを残します。

## 人が判断する必要があること

読み取れない原本の値、複数ロット間の帰属、帳票の真正性、改訂版の適用、製品と単位の同一性、規格外値の意味、ロット代表値を工程能力に使えるかどうか、正式な品質承認は、人または会社の承認手順が判断する対象です。高度なローカルモデルやクラウドAIを追加しても、この境界は変えません。
